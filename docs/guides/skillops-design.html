SkillOps Agent 설계도

업무 담당자가 SKILL.md를 자기 업무 흐름에 맞춰 고쳤을 때 깨지는 에이전트 서비스를, 실행 증거로 진단하고 검증된 수정안을 제안하는 에이전트. 무대가 되는 서비스와 주인공 에이전트를 2일 안에 함께 만든다.

무대 주문 처리 에이전트 skill SKILL.md, 고치는 사람은 개발자가 아닌 업무 담당자 harness Spring AI로 직접 구축 원칙 LLM은 제안하고 harness가 판정한다

STAGE · 주문 처리 서비스

SKILL.md 6개로 돌아가는 주문 에이전트

주문이 들어오면 orchestrator skill이 정한 순서대로 단계 skill을 실행한다. 각 skill은 frontmatter에 입력·출력·의존을 선언하고, 본문은 담당자가 쓰는 자연어 절차다.

order-flow⟶ order-intake→ inventory-check→ payment→ shipping-reserve→ notify
  • 재고·결제·배송·알림은 mock 어댑터. 데모에 외부 연동은 없다.
  • 모든 실행은 구조화된 트레이스로 남는다 (어떤 skill이 어떤 입력으로 무엇을 반환/실패했나).
  • SKILL.md 저장은 곧 버전이다. 되돌리기는 1클릭.

HERO · SkillOps Agent

장애를 진단하고, 검증된 수정안을 제안

담당자의 수정으로 주문이 실패하면(또는 저장 시점에) 트레이스·diff·레지스트리를 읽고 원인을 실험으로 확정한 뒤, 깊이가 다른 수정안 2~3개를 격리된 workspace에서 실제로 돌려 통과한 것만 제안한다.

  • "원래대로 되돌리기"는 해결책이 아니다. 담당자의 의도는 보존되어야 한다.
  • 근본 수정 = 바뀐 skill 하나가 아니라 하위 skill의 계약(입출력)까지 맞추는 것.
  • 설명은 trace ID와 시나리오 ID를 인용해야 한다. 증거 없는 문장은 금지.

병렬 작업의 전제

아래 다섯 가지가 확정되면 다섯 레인은 서로를 기다리지 않는다. W5가 문서로 관리하고, 변경은 13시·18시 두 번만 반영한다.

① SKILL.md frontmatter

---
name: payment
description: 주문 금액을 결제한다. 결제 정책은 여기서 바꾼다.
inputs:     [order.id, order.total, inventory.reserved]
outputs:    [payment.id, payment.status]
depends_on: [inventory-check]
owner: 재무팀
version: 4
---
# 결제 절차
1. 재고 예약(inventory.reserved)이 true인 주문만 진행한다.
2. 결제 어댑터를 호출하고 payment.id를 받는다.
3. 실패하면 payment.status를 FAILED로 두고 끝낸다.

orchestrator인 order-flow는 steps: [...]로 순서를 선언한다. 계약 일관성 검사는 steps 순서대로 inputs가 앞선 outputs에서 공급되는지 본다.

② 트레이스 레코드

{ "run_id": "r_01J9…", "order_id": "o_1024",
  "mode": "live",            // live | dry-run

    { "skill": "inventory-check", "version": 3,

{ "id": "g-03", "name": "선입금 2건 주문",
