SkillOps 도구 12개

SkillOps Agent는 주문 처리 서비스 안을 직접 들여다보지 못합니다. 서비스가 열어 둔 도구 12개를 불러야만 기록을 읽고, 수정안을 시험하고, 결과를 남길 수 있습니다. 이 페이지는 각 도구가 하는 일과, Agent가 그 도구들을 어떤 순서로 부르는지를 쉬운 말로 정리한 것입니다.

도구의 영어 이름은 코드에서 찾을 때 쓰는 이름입니다. 설명과 그림은 우리말 이름만 따라가며 읽으면 됩니다.

읽는 도구 6개 · C-1 담당 바꾸고 확인하는 도구 6개 · C-2 담당
먼저 알아 둘 말 도구 12개 부르는 순서 C-1과 C-2가 맞물리는 곳 아직 정할 것

용어

먼저 알아 둘 말

설명과 그림에서는 아래의 쉬운 말을 씁니다. 굵은 글씨 옆의 작은 글씨는 설계 문서와 코드에서 같은 것을 가리키는 이름입니다.

skill SKILL.md
업무 지침서 한 장입니다. 주문은 여섯 개의 skill이 차례로 실행되면서 처리됩니다.
버전 version
skill을 저장할 때마다 1씩 올라가는 번호입니다. 예전 버전도 지워지지 않고 남습니다.
받는 값 · 내놓는 값 inputs · outputs
SKILL.md 맨 위에 적어 두는 칸입니다. 앞 skill이 내놓은 값을 뒤 skill이 받아 쓰는 방식으로 skill들이 이어집니다.
실행 기록 trace · run_id
주문 한 건을 처리하는 동안 skill마다 무엇을 받고 무엇을 내놓았는지 적어 둔 기록입니다. 실행 번호로 찾습니다.
변경 덩어리 diff · hunk
두 버전을 비교했을 때 바뀐 곳 하나하나입니다. 세 군데가 바뀌었으면 덩어리도 세 개이고, 각각 번호가 붙습니다.
연습 공간 workspace · sandbox
운영 중인 skill을 건드리지 않으려고 따로 떼어 낸 복사본입니다. 고치고 시험하는 일은 모두 여기서 합니다.
모의 실행 dry-run
재고·결제·배송·알림을 실제로 일으키지 않고, 미리 정해 둔 응답만 받으면서 주문을 처리해 보는 것입니다.
시험 주문 scenario
채점 기준이 정해져 있는 주문입니다. 언제나 통과해야 하는 기준 주문 6건(g-01~g-06)과, 실패한 주문을 그대로 옮긴 재현 주문이 있습니다.
확인 조건 assertion
결과가 맞는지 보는 한 줄짜리 조건입니다. 예를 들어 "결제 상태는 결제 완료여야 한다" 같은 것입니다.
담당자의 의도 intent
담당자가 skill을 고쳐서 바꾸려던 업무 규칙입니다. 좋은 수정안은 오류를 없애면서 이 의도도 살려 둡니다.
수정 제안서 proposal · evidence
Agent가 진단을 마치고 남기는 결과물입니다. 원인, 의도, 후보 수정안, 시험 결과와 그 근거가 들어 있습니다.
운영 반영 · 되돌리기 promote · rollback
연습 공간에서 검증한 내용을 실제 skill로 옮기는 일, 그리고 문제가 생겼을 때 이전 버전으로 돌려놓는 일입니다.

C-2 담당

연습 공간 만들기, 수정 적용하기, 시험 주문 돌리기는 연습 공간 안에서만 일합니다. 제안서 저장하기는 결과를 남기기만 합니다. 실제 운영 중인 skill을 바꾸는 도구는 운영에 반영하기와 이전 버전으로 되돌리기, 두 개뿐입니다.

이 밖에 서비스와 Agent가 연결됐는지만 확인하는 ping이 하나 더 있습니다. 진단에는 쓰이지 않습니다.

흐름

Agent가 도구를 부르는 순서

주문 하나가 실패한 경우를 따라가 봅니다. 위에서 아래로 시간이 흐르고, 가로 화살표는 "이 도구를 부른다"는 뜻입니다. 동그라미 안의 숫자가 부르는 순서입니다.

C-1 읽는 도구 C-2 바꾸고 확인하는 도구 Agent가 도구 없이 혼자 판단 서비스와 운영자 필요할 때만 부름

단계별로 읽기

예시로 쓰는 장애 F1. 물류팀 담당자가 재고 확인 skill에서 내놓는 값의 이름을 '예약 가능 수량'으로 바꾸고, '예약 여부' 값은 필요 없다며 지웠습니다. 그런데 결제 skill은 '예약 여부' 값을 받아야 결제를 진행하기 때문에 주문이 결제 단계에서 실패합니다.

  1. 시작

    알림 받기

    주문 처리 서비스가 주문 실패를 감지하면 SkillOps Agent에 알림을 보냅니다. 알림에는 실패한 실행의 번호가 들어 있습니다. 이때는 아직 도구를 부르지 않습니다.

    F1 예시주문 한 건이 결제 단계에서 멈추고, 그 실행 번호가 담긴 알림이 옵니다.

  2. 1단계

    살펴보기

    어디서 왜 멈췄고, 최근에 무엇이 바뀌었나?

      어느 skill에서 어떤 오류로 멈췄는지, 그때 각 skill이 몇 번째 버전이었는지 확인합니다.

    • 3
      skill 목록 보기list_skills

      지금 각 skill의 버전과 받는 값, 내놓는 값을 확인합니다.

    • 4
      두 버전 비교하기diff_skill

      최근에 바뀐 skill에서 무엇이 바뀌었는지 덩어리별로 받습니다.

    • 5
      skill 본문 읽기get_skill

      바뀐 skill과, 그 skill이 내놓는 값을 받아 쓰는 skill의 본문을 읽습니다.

      연결 관계 보기get_dependency_graph

      끊긴 연결이 있는지, 바뀐 skill의 영향이 어디까지 닿는지 봅니다.

    판단모은 내용을 바탕으로 AI가 "이 덩어리가 원인일 것"이라는 후보를 세웁니다.

    F1 예시결제 skill이 "예약 여부 값을 찾을 수 없다"는 오류로 멈췄습니다. 연결 관계 보기에서도 결제 skill이 받아야 할 '예약 여부'를 내놓는 skill이 없다고 나옵니다. 재고 확인 skill의 변경 덩어리 가운데 하나가 원인 후보가 됩니다.

  3. 2단계

    원인 확인

    정말 그 덩어리 때문인가?

    • 7
      연습 공간 만들기create_workspace

      담당자가 고치기 전 버전으로 연습 공간을 만듭니다.

    • 8

    • 9

    판단실패가 다시 나타나면 그 덩어리가 원인으로 확정됩니다. 나타나지 않으면 다음 덩어리로 7~9번을 되풀이합니다. 어느 덩어리에서도 실패가 나타나지 않으면 1단계로 돌아가 원인 후보를 다시 세웁니다.

    F1 예시'내놓는 값' 목록을 바꾼 덩어리를 넣었을 때 결제가 다시 실패해야, 그 덩어리가 원인으로 확정됩니다.

  4. 3단계

    의도 정리

    담당자는 원래 무엇을 하려고 했나?

    도구를 부르지 않는 단계AI가 앞에서 읽은 변경 내용을 보고 담당자의 의도를 한 문장으로 정리합니다. 그리고 그 의도가 지켜졌는지 볼 확인 조건을 만듭니다. 이 조건이 있어야 담당자의 수정을 그냥 되돌리는 방법을 걸러 낼 수 있습니다. 의도를 제대로 읽었는지는 7단계 승인 화면에서 담당자가 확인합니다.

    F1 예시의도는 "재고 수량이 아니라 예약 가능 수량으로 판단하고 싶다"입니다. 확인 조건은 "재고 확인 결과에 예약 가능 수량이 들어 있어야 한다"가 됩니다.

  5. 4단계

    후보 만들기

    어떻게 고칠 수 있나?

    도구를 부르지 않는 단계AI가 고칠 방법을 2~3개 만듭니다. 바뀐 skill만 고치는 방법, 값을 주고받는 skill까지 함께 맞추는 방법, 실행 순서를 다시 짜는 방법 가운데서 고릅니다.

    F1 예시(가) 재고 확인 skill을 원래대로 되돌린다. (나) 재고 확인 skill이 '예약 여부'를 다시 내놓게 하고, 본문에 "예약 가능 수량이 0보다 크면 예약된 것으로 본다"고 적는다. (다) 결제 skill이 '예약 가능 수량'을 받아 쓰도록 바꾼다.

  6. 5단계

    후보 시험

    이 후보로 정말 고쳐지나? 후보마다 되풀이합니다.

    • 10
      연습 공간 만들기create_workspace

      후보마다 지금 운영 중인 상태로 새 연습 공간을 만듭니다.

    • 11
      수정 적용하기apply_patch

      후보 수정안을 넣고, 끊긴 연결이 남았는지 목록으로 받습니다.

    • 12
      시험 주문 돌리기run_scenarios

      기준 주문 6건과 실패 재현 주문을 의도 확인 조건까지 붙여서 각각 2번씩 돌립니다.

    • 13
      실행 기록 자세히 보기get_trace

      필요할 때만떨어진 후보가 있으면 어디서 틀렸는지 봅니다.

    판단실패했던 주문이 통과하고, 원래 잘 되던 주문이 그대로 통과하고, 의도 확인 조건까지 통과해야 합격입니다. 합격한 후보가 없으면 4단계로 한 번 돌아가고, 그래도 없으면 "쓸 수 있는 수정안 없음"을 근거와 함께 보고합니다. 이것도 정상적인 결과입니다.

    F1 예시F1 문서가 예상하는 결과는 이렇습니다. (가)는 의도 확인 조건에서 떨어지고, (나)와 (다)는 합격합니다.

  7. 6단계

    제안서 남기기

    무엇을 추천하나?

    판단합격한 후보끼리는 연결이 끊긴 곳 없이 이어지는지, 손댄 skill이 적은지로 순위를 매깁니다.

    • 14
      제안서 저장하기save_proposal

      원인, 의도, 후보, 시험 결과를 저장합니다. 설명에는 시험 실행 번호만 근거로 듭니다.

    F1 예시(나)가 1순위입니다. 손댄 skill이 재고 확인 하나뿐이기 때문입니다. (다)는 결제 skill까지 바꿔야 해서 2순위입니다.

  8. Agent의 진단은 여기까지입니다. 아래는 운영자가 승인한 뒤에 일어납니다.
  9. 7단계

    운영 반영

    승인한 수정안을 실제로 적용합니다.

    운영자는 화면에서 후보들을 비교하고, 담당자는 Agent가 정리한 의도가 맞는지 확인합니다. 승인하면 서비스가 승인 번호를 발급합니다.

    • 15
      운영에 반영하기promote_workspace

      서비스가 승인 번호와 함께 부릅니다. 반영한 직후 점검 주문을 돌립니다.

    • 16
      이전 버전으로 되돌리기rollback

      필요할 때만점검 주문이 실패하면 반영 전 버전으로 돌려놓습니다. 운영자가 화면에서 직접 되돌릴 때도 같은 기능을 씁니다.

    담당자가 의도를 잘못 읽었다고 답하면, 고친 의도로 4~6단계를 다시 돌립니다.

skill이 저장됐다는 알림으로 시작하는 경우에는 아직 실패한 주문이 없으므로, 4번 두 버전 비교하기와 6번 연결 관계 보기로 시작합니다. 이 경로는 일정이 밀리면 가장 먼저 빼기로 한 부분이라 그림에서는 생략했습니다.

협업

C-1과 C-2가 맞물리는 곳

두 사람의 도구는 따로 떨어져 있지 않습니다. 아래 네 곳에서는 한쪽이 만든 것을 다른 쪽이 그대로 씁니다. 1일차 11시 접점 회의에서 이 네 가지를 먼저 맞추면 됩니다.

skill 버전 저장소

C-1 버전 저장소→연습 공간 만들기운영에 반영하기

C-1이 만드는 버전 저장소에는 skill의 모든 버전이 남습니다. 연습 공간 만들기는 여기서 몇 번째 버전의 본문을 꺼내 복사본을 만들고, 운영에 반영하기는 검증된 내용을 여기에 새 버전으로 저장합니다.

함께 정할 것본문을 꺼내는 기능과 새 버전을 저장하는 기능의 이름, 받는 값, 돌려주는 값

변경 덩어리 번호

두 버전 비교하기→수정 적용하기

두 버전 비교하기가 매긴 덩어리 번호와 내용을 2단계의 수정 적용하기가 그대로 받아서, 덩어리 하나만 넣을 수 있어야 합니다. 번호를 매기는 기준이 서로 다르면 원인 확인 결과가 엉뚱한 덩어리를 가리킵니다.

함께 정할 것덩어리를 나누는 기준, 그리고 수정 적용하기에 덩어리를 건네는 형식

실행 기록

시험 주문 돌리기→C-1 실행 기록 저장소→실패한 주문 목록 보기

시험 주문 돌리기가 모의 실행한 결과도 C-1의 실행 기록 저장소에 남고, 채점도 그 기록을 읽어서 합니다. 실행 기록에는 실제 실행인지 모의 실행인지, 어느 연습 공간에서 돌았는지를 적는 칸이 이미 있습니다.

함께 정할 것실패한 주문 목록에는 실제 실행만 보여 주고, 모의 실행이 실패했을 때는 실패 알림을 보내지 않기. 그러지 않으면 시험 중에 생긴 실패가 새 진단을 끝없이 일으킵니다.

연결 검사

연결 관계 보기와수정 적용하기는 같은 검사를 씁니다

연결 관계 보기가 알려 주는 끊긴 연결과 수정 적용하기가 돌려주는 끊긴 연결은 같은 검사에서 나와야 합니다. 이 검사는 A가 만드는 skill 정보 검사 기능에 들어 있습니다. 각자 검사 코드를 따로 만들면 같은 skill 묶음을 두고 서로 다른 답을 낼 수 있습니다.

함께 정할 것두 도구 모두 A의 검사 기능을 불러 쓰고, 끊긴 연결을 같은 모양으로 돌려주기

도구 코드는 같은 폴더(service/…/mcp/)에 들어갑니다. 읽는 도구 묶음은 C-1이, 바꾸고 확인하는 도구 묶음은 C-2가 맡고, 같은 파일을 둘이 함께 고치지 않습니다.

확인할 것

1차안에서 아직 정하지 않은 것

계약 초안을 흐름대로 따라가 보면 비어 있는 곳이 네 군데 보입니다. 계약을 확정하기 전에 정리할 후보입니다.

  1. 1

    바뀌기 전 버전을 찾는 방법 C-1 · B

    실패 알림에는 실행 번호만 들어 있습니다. 실행 기록으로 지금 버전은 알 수 있지만, 마지막으로 잘 돌던 때가 몇 번째 버전이었는지는 지금 도구로 알 수 없습니다. 두 버전 비교하기에 어떤 두 버전을 넣을지 정하려면 이 값이 필요합니다. skill 목록에 직전 버전과 저장 시각을 넣거나, 화면용 API에만 있는 버전 이력 조회(/api/skills/{name}/versions)를 도구로도 여는 방법이 있습니다.

  2. 2

    재현 주문과 의도 확인 조건을 건네는 방법 C-2 · B

    시험 주문 돌리기는 지금 시험 주문의 번호만 받습니다. 하지만 재현 주문은 실패 기록에서 그때그때 만들어지고, 3단계에서 만든 의도 확인 조건도 채점에 더해야 합니다. 내용을 통째로 받을지, 먼저 등록하는 도구를 따로 둘지 정해야 합니다.

  3. 3

    덩어리 하나를 넣는 형식 C-1 · C-2 · B

    지금 계약에서 수정 적용하기는 고칠 내용을 글자 그대로 받습니다. 원인 확인 단계에서는 덩어리 번호만 건네는 편이 더 간단할 수 있습니다. 어느 쪽을 고르든 두 버전 비교하기가 돌려주는 모양과 짝이 맞아야 합니다.

  4. 4

    운영 반영을 누가 부르나 C-2 · A

    계약의 도구 표에는 운영에 반영하기가 Agent용 도구로 올라 있지만, 승인 API 설명에는 서비스가 직접 부른다고 적혀 있습니다. 승인 번호가 없으면 거부되므로 위험하지는 않습니다. 다만 Agent 쪽 도구 목록에 둘지, 서비스 안의 기능으로만 둘지 정해 두면 헷갈리지 않습니다.
