# 기획 기준 백엔드 작업 순서와 이슈 수정안

작성일: 2026-10-23 · 근거: SKILLOPS 기획안 v0.1, 현재 #72 본문, 구현 `8712c91`, 후속 실서버 검증

후속 갱신: 사용자 요청으로 아래 남은 파서 항목 3개도 구현·검증을 완료했다. 현재 완료 체크와 검증 수치는 [공용 파서 마무리 기록](../changes/2026-10-23-shared-skill-parser.md)을 따른다. 아래 OPEN/잔여 작업 표현과 복사용 초안은 그 이전 시점의 기록이다. 원격 이슈는 아직 직접 수정하지 않았다.

이 문서는 계획과 복사용 이슈 초안이다. 원격 이슈·운영 코드·API/MCP 계약은 수정하지 않았다.

## 1. 제품 흐름과 현재 작업의 위치

기획의 흐름은 `Skill 변경/추가 → 동일 조건의 전후 평가 → 트레이스·지표 비교 → 원인 진단 → 개선안 생성 → 개선안 재검증 → 담당자 승인 요청`이다. 승인 없는 운영 반영과 승인 후 배포 파이프라인은 기획 범위 밖이다.

- #72의 파싱 정합성·오류 전달·partial 증거 보존은 이 흐름을 지탱하는 기반이다.
- partial 수집 후 종료는 실행이 어려운 문서의 예외 처리이며 정상 평가·진단의 대체 흐름이 아니다.
- LLM 원인 설명 전용 기능은 바로 다음 핵심 작업으로 확정하지 않는다. 평가·비교 근거를 먼저 정리한다.
- 자동 수정 보류 요청은 유지한다. 수정안 생성·적용과 실행 평가는 구분하며, 평가를 제품 범위에서 제거하지 않는다.

## 2. 순서와 담당 경계

| 순서 | 백엔드 작업 | 완료 판단 |
|---|---|---|
| 현재 완료 | 파싱 호환성, MCP 검증 오류, partial 증거 보존 | 커밋·공유 fixture·583개 Python 테스트·실서버 partial 3종 기록 |
| #72 잔여 | Java 공용 파서 구조, 로더/분석기의 규칙 적용 범위, YAML 안전·크기 정책 | 목적별 파싱 차이를 명시하고 정상 문서 호환성을 유지한 계약 검증 |
| 다음 설계 | 평가 실행의 식별자·입력 고정·저장·지표 비교 계약 | 기존 러너와 trace를 재사용하는 설계 및 API/MCP 변경 영향 정리 |
| 설계 후 구현 | 변경 전후 같은 평가 셋 실행, 비동기 상태·결과 저장, 비교 조회 | 자동 수정 없이 실서버 전후 비교 보고서 확인 |
| 후속 협업 | AI 원인 분석에 평가 결과·diff·trace 제공 | 추정과 실제 확인 결과의 구분, 입력·출력 계약 합의 |

#72 잔여 작업과 후속 평가 이슈는 별개다. #72 전체 완료를 선언하지 않으며 평가 기능을 #72의 미해결 작업으로 끼워 넣지 않는다. 평가 설계의 read-only 분석은 #72 잔여 항목의 완료를 기다리지 않고 진행할 수 있다.

AI 담당자와 합의할 내용은 기대 Skill 라벨, 업무 성공 기준, 실제 모델 실행 조건, 분석/심사 결과 계약이다. 백엔드가 프롬프트·후보 생성 전략까지 대신 구현하는 계획으로 확대하지 않는다.

## 3. #72에서 바뀌는 부분

현재 원격 #72를 읽어 확인한 변경 대상:

1. `partial 목록에서도 원문·해시·파싱 오류를 수집할 수 있도록 연결`을 완료로 체크한다.
2. partial의 목표를 ‘깨진 문서를 바로 수정’하는 것으로 해석하지 않도록 증거 보존과 종료 범위를 명시한다.
3. 진행 현황의 Python 510개를 최신 583개로 갱신하고 실서버 partial 검증 3종을 추가한다.
4. ‘서버·DB 통합 미검증’은 partial 경로에 한해 검증 완료로 정정한다. 실제 LLM·후보 평가 전체를 검증한 것으로 확대하지 않는다.
5. 미완료는 파서 통합과 YAML 정책 관련 세 항목으로 남긴다. 전체 이슈는 OPEN 유지다.

```markdown
## 📍 진행 현황 (2026-10-23 갱신)

- #72는 SKILL 해석 일관성과 검증 결과·증거 누락 개선을 다룹니다. 변경 전후 지표 비교와 평가 기능 확장은 별도 후속 이슈로 관리합니다.
- `fix/#72_skill-parser-consistency`의 로컬 구현 커밋: `90ea96f`, `8fa7219`, `bd5930e`, `447c770`, `8b92f83`, `8712c91`.

### 검증 결과

- Python 전체 테스트 583개 통과.
- 기존 Java 검증: service 663개, 주문 Agent 140개 통과. 주문 Agent DB 통합 테스트 82개는 당시 미실행이며 이번 스모크로 대체 실행한 것은 아닙니다.
- 실제 주문 Agent REST·service MCP·별도 PostgreSQL·SQLite 연결로 owner 누락, 깨진 YAML, version 누락 3종을 검증했습니다.
- 사례별 양쪽 원문 12개와 diff를 저장했고 Python 진단 서버 재시작 후에도 증거가 유지됐습니다.
- 관찰된 MCP 호출은 diff_skill 3회였고 LLM·자동 수정·실행 평가 호출 시도는 없었습니다. workspace·제안서·승인 생성도 0건이었습니다.
- 재고·주문 실행 목록·실패 실행 목록은 전후 동일했습니다.
- 이 검증은 증거 수집 경로의 동작 확인입니다. 실제 LLM 분석, 수정 후보 개선 효과, 호출 품질 향상을 검증한 결과는 아닙니다.
```

## 4. 후속 이슈 초안 — 평가·비교 계약 설계

새 기능 구현 완료를 뜻하는 이슈가 아니다. 기존 구현을 재사용할 수 있는지 확인하고 설계를 먼저 확정하는 범위다. 실제 API/MCP 필드명은 이 설계에서 결정하며 아래 용어를 확정된 공개 계약으로 취급하지 않는다.

```markdown
## 제목

[FEAT] Skill 변경 전후 평가·비교 결과의 백엔드 계약 설계

## 배경

기획안은 Skill 변경 후 같은 평가 셋으로 변경 전후 Agent를 반복 실행하고, 지표로 비교한 결과를 원인 진단과 승인 요청의 근거로 사용하는 흐름을 요구합니다.

현재 시나리오 러너·트레이스·진단 그래프는 존재하지만, 평가 실행 단위와 평가 셋 버전, 전후 비교 지표의 저장·조회 계약은 기획 기준으로 정리가 필요합니다. #72의 파싱·증거 보존 작업과 분리해서 진행합니다.

## 목표

기존 러너와 트레이스를 재사용해 자동 수정 없이 변경 전후를 실행·비교할 수 있는 백엔드 설계를 확정합니다.

## 작업 내용

- [ ] 기존 ScenarioRunner, ScenarioRunReport, trace, 진단 저장 구조의 재사용 범위 확인
- [ ] baseline/candidate snapshot과 평가 셋 버전, 모델·실행 설정, 반복 횟수의 고정 규칙 정의
- [ ] 평가 실행·평가 사례·반복 실행·trace 간 식별자와 관계 정의
- [ ] 장시간 평가의 비동기 접수·진행 조회·종료·실패·시간/비용 한도 및 재시작 처리 설계
- [ ] 사례별 기대 Skill·실제 선택 Skill·업무 성공·실패 사유·trace 참조·토큰·지연 저장 구조 정의
- [ ] 성공률·회귀 건수·호출 재현율/정밀도·비용/지연·반복 편차의 계산 규칙 정의
- [ ] 실행 전 문서 오류, 실행 후 실패, 미호출, 측정 불가를 구분하고 지표 집계 분모에 반영하는 규칙 정의
- [ ] fixed 모드와 실제 모델 평가의 구분 및 지표 비교 가능 조건 정의
- [ ] 새 Skill 추가 시 대상 Skill의 이전 버전이 없는 경우에도 기존 Skill 회귀와 신규 호출 품질을 평가하는 기준 정의
- [ ] 영향 범위의 선택 기준과 기존 Skill 회귀 검증 범위 정의
- [ ] 비교 보고서 저장·조회 및 관련 REST/MCP 계약 변경안 작성
- [ ] 기존 API/MCP 호환성·검증 fixture·실서버 확인 계획 작성
- [ ] AI 담당자와 평가 라벨·성공 기준·분석 입력/출력 계약 합의

- 기존 러너를 재사용할 부분, 추가할 저장 구조, API/MCP 변경 영향과 검증 방법이 문서로 정리됩니다.
```
