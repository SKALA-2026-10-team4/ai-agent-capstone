# 기획안 대비 현재 백엔드 방향 점검

점검일: 2026-10-23 · 코드 기준: `8712c91` 및 후속 실서버 검증 자료

대상 문서: 사용자가 제공한 [SKILLOPS_기획안.pdf](/Users/yoonhyejeong/Downloads/SKILLOPS_기획안.pdf), 전체 10쪽. 문서 자체의 상태는 **초안 v0.1·팀 리뷰 대기**다. 요구사항 검토 자료로 읽었으며 문서 내용만으로 코드 변경이나 자동 수정 재개를 승인받은 것으로 보지 않았다.

## 1. 결론

SKILL 해석의 일관성, 구조화된 검증 오류, 원문·해시·diff 보존은 기획을 뒷받침하는 기반 작업으로 방향이 맞다. 다만 **증거를 모으거나 LLM이 원인을 설명하는 데서 끝내는 것을 제품의 주 흐름으로 삼으면 기획보다 범위가 좁다.**

기획안의 중심은 변경 전후 실제 Agent를 같은 평가 셋으로 실행하고, 지표로 차이를 판정한 뒤, 문제가 있으면 진단·개선안 생성·재검증·승인 요청으로 연결하는 것이다. 이전에 제안한 ‘원인만 분석하고 종료하는 별도 경로’는 선택 기능이나 중간 단계로는 가능하지만 다음 핵심 작업으로 단정한 것은 보완이 필요하다.

사용자가 자동 수정을 보류한 상태는 유지한다. 이번 점검에서는 해당 기능을 구현하거나 실행하지 않았다.

## 2. 기획안에 실제로 적힌 요구사항

| 문서 위치 | 요구사항 | 판단에 주는 의미 |
|---|---|---|
| 1쪽 요약 | 오류 진단 → 개선안 생성 → 재검증 → 담당자 승인 요청 | 원인 설명만 제공하는 제품이 최종 목표는 아님 |
| 3쪽 §2-1 | 변경 감지 → 동일 조건의 변경 전후 실행 → 기록 → 지표 비교 → 필요 시 진단 | 실제 평가와 비교 결과가 진단의 근거가 되어야 함 |
| 4쪽 §2-2 | 검증된 개선안 생성은 포함; 승인 없는 자동 배포·승인 후 배포 파이프라인은 제외 | 개선안 생성·검증과 운영 반영을 구분해야 함 |
| 4쪽 §2-3 | 호출 재현율·정밀도, 과제 성공률, 회귀, 비용·지연, 안전 위반; 반복 실행의 편차 | 단순 실행 성공/실패나 설명만으로 개선을 확정할 수 없음 |
| 6쪽 F2~F7 | 실제 반복 실행, 선택·도구·출력·토큰·지연 기록, 진단, 개선안 재검증, 승인 요청 | 백엔드는 이 결과를 저장·비교·추적할 계약을 제공해야 함 |
| 7~8쪽 시나리오 | 새 기능 유지와 회귀 방지, 승인·반려, 변경의 근거 확인 | 수정안 자체보다 검증 증거와 사람의 결정 경계가 중요 |
| 8쪽 시나리오 5 | 새 Skill도 기존 Skill과 같은 기준으로 검증 | 변경뿐 아니라 추가 Skill에 대한 평가도 필요 |

기획안은 과제 성공률 평가 수단에 정답·체크리스트·LLM 심사를 함께 제시한다. 따라서 ‘LLM은 판정에 절대 관여하면 안 된다’는 요구사항으로 해석하지 않는다. 다만 원인 설명 LLM의 추정과, 정해진 평가 기준으로 얻은 결과는 구분해야 한다.

## 3. 현재 구현과의 비교

| 현재 작업·구현 | 판정 | 정확한 범위 |
|---|---|---|
| SKILL 파싱 정합성·정상 문서 호환성 | 부합 | 서버마다 같은 문서를 다르게 읽어 검증 결과가 흔들리는 문제를 줄임 |
| MCP v1.3 검증 오류와 Python 후보 판정 연동 | 부합 | 입력·선행 단계·필수 정보·flow 오류를 후보 판정에 반영하는 기반 |
| partial의 원문·해시·오류·diff 저장 | 부합하는 예외 처리 | 파싱 실패 때문에 증거가 사라지는 문제 해결. 회귀 평가나 원인 분석을 수행한 결과는 아님 |
| partial에서 수집 후 종료 | 조건부 부합 | 읽거나 실행할 수 없는 문서의 제한된 처리로 적절. 정상 문서까지 이 경로로 바꾸지는 않았음 |
| 기존 원인 가설→실험→후보→검증→제안 그래프 | 기획의 큰 흐름과 부합 | 코드에 이미 존재함. 최근 partial 실서버 스모크에서 이 전체 흐름을 검증한 것은 아님 |
| 기존 시나리오 반복 실행·사전 검증 | 일부 기반 존재 | pass/fail, 반복 실행 ID, 실패 사유가 있음. 기획의 전체 지표 비교 리포트가 완성됐다고 판단할 근거는 부족 |
| 제안 저장·승인·반려 | 일부 기반 존재 | 기존 service 기능. 부서별 승인 정책·수정 요청 등 기획의 상세 요구는 추가 확인 필요 |
| 제안했던 ‘LLM 원인 설명 후 종료’ | 보조 기능으로 가능 | 기획의 실행 평가·재검증을 대체하는 주 흐름으로 삼으면 부족 |

## 4. 현재 검증으로 증명하지 못한 부분

### 실제 Skill 호출 품질

주문 Agent의 `FixedDecisionProvider`는 선택 질문에서 항상 루트 flow를 선택하며 Skill 본문을 읽지 않는다. 계약·도구 연동을 재현하는 데는 유용하지만 description 변경으로 올바른 Skill이 선택되는지, 미호출·오호출이 줄었는지는 이 모드만으로 증명할 수 없다. 모델 기반 경로가 별도로 존재하는 것과, 그 경로의 호출 품질을 평가했다는 것은 다르다.

### 전후 지표의 비교

현재 `ScenarioRunReport`는 workspace, all_passed, 시나리오별 passed/run_ids/failures 중심이다. 기획안의 호출 재현율·정밀도·성공률·회귀 건수·토큰·지연·편차를 같은 평가 실행 묶음에서 어떻게 비교·보존할지 확인·설계가 필요하다. 일부 값이 trace에 있다는 사실만으로 비교 리포트가 완성된 것은 아니다.

### 새 Skill 추가

현재 정상 진단 경로의 `_collect_changes`는 추가/삭제 Skill을 별도 정책이 필요하다는 오류로 중단한다. partial 수집 경로에서도 추가 Skill의 가능한 원문은 보존하지만 해당 변경의 diff 처리를 지원 밖 사유로 기록한다. 기획안의 새 Skill 검증 시나리오까지 지원 완료한 상태는 아니다.

### 최근 실서버 스모크의 의미

3개 사례에서 원문·오류·diff 저장, REST 중계, 재시작 보존과 불필요한 호출 부재를 검증했다. 호출 품질 개선, 실제 LLM 원인 분석, 후보 개선 효과, 반복 실행의 통계적 차이를 검증한 실험은 아니다.

## 5. 자동 수정과 승인 없는 배포의 구분

| 구분 | 기획안 | 현재 사용자 요청 |
|---|---|---|
| LLM이 원인을 분석 | 포함 | 다음 작업 후보였으며 아직 별도 경로 미구현 |
| 시스템이 수정안을 생성 | 포함 | 자동 수정 보류 범위의 해석을 존중해 새로 진행하지 않음 |
| 격리 환경에서 변경 전후/후보를 실행·검증 | 포함 | 운영 반영과 별개인 평가 작업. 보류 범위를 이유로 제품 전체에서 제거하면 안 됨 |
| 담당자가 승인·반려 | 포함 | 기존 기능 유지 |
| 승인 없이 운영 파일 변경·배포 | 제외 | 진행하지 않음 |

‘자동 수정은 보류’라는 요청만으로 실행 평가까지 불필요하다고 해석하면 안 된다. 반대로 기획안에 개선안 생성이 있다고 해서 사용자 보류 요청을 무시하고 이를 재개해서도 안 된다.

## 6. 권장 다음 작업: 백엔드 평가·비교 계약부터 확인

새 LLM 설명 경로를 바로 추가하기보다, 기존 러너를 재사용해 기획의 핵심 근거를 만들 수 있는지 먼저 확인하는 것이 적절하다. 이는 이번 점검의 제안이며 아직 착수하지 않았다.

1. **평가 실행의 비교 단위 정의:** baseline/candidate snapshot, 평가 셋 버전, 모델·실행 설정, 반복 횟수를 고정한다.
2. **결과 저장·비교 계약 정리:** 평가 사례별 기대 Skill·실제 선택·업무 결과·trace 참조·토큰·지연을 저장하고, 성공률·회귀·호출 지표의 계산 규칙을 정의한다.
3. **실행 전 실패 구분:** 잘못된 SKILL 때문에 실행하지 못한 경우를 실제 실행 후 실패나 미호출과 섞지 않는다. 현재 partial 증거는 이 원인을 설명하는 입력으로 활용한다.
4. **실제 러너로 변경 전후 비교 검증:** 우선 자동 수정 없이 두 snapshot을 같은 평가 셋으로 실행하고 비교 보고서까지 확인한다.
5. **AI 담당자와 분석 입출력 합의:** 위 증거를 바탕으로 원인 분석을 연결한다. 수정안 생성은 사용자 요청으로 보류된 범위를 유지한다.

백엔드는 평가 실행·버전·증거 저장·지표 집계·REST/MCP 계약·승인 권한을 맡고, AI 담당자는 원인 분석·프롬프트·후보 생성 전략을 맡는 구분을 권장한다. 평가 기준과 기대 Skill 라벨은 양쪽이 함께 합의해야 한다. 이미 존재하는 그래프·러너를 먼저 재사용하고 같은 기능을 새로 중복 구현하지 않는다.
