# PM 공유용 — Backend·MCP 리팩토링 필요사항

> **과거 검토 기록 — 기준 `ec39713`.** 이 문서의 “현재”, 미완료 항목, 테스트 수와 줄 번호는 작성 당시 기준입니다. 최신 구현·계약·#72 완료 상태는 [리뷰 문서 안내](../README.md)를 우선합니다. 아래 제안을 현재 API나 새 작업 승인으로 간주하지 않습니다.

작성 기준일: 2026-10-22 · 대상: 현재 SkillOps 코드 · 목적: 기존 기능을 유지하면서 개발·검증·인수인계 비용을 줄이기 위한 정리.

## 1. 이번에 검토할 범위

현재 코드는 주문 실행, 변경 진단, 수정 후보 시험, 제안서 저장, 승인 기록까지 여러 서비스를 연결하고 있습니다. 이 과정에서 유사한 코드가 여러 곳에 생겼고, 한 함수가 여러 역할을 담당하거나 현재 실행 흐름과 이전 코드가 함께 남은 부분을 확인했습니다.

이번 문서의 **리팩토링은 사용자가 받는 결과와 API 약속을 유지하면서 내부 코드의 구조를 정리하는 작업**을 의미합니다. 목적은 다음 변경에서 수정할 곳을 쉽게 찾고, 기존 기능이 예상치 못하게 달라질 가능성을 줄이는 것입니다.

예를 들어 ‘MCP 응답을 만드는 중복 코드를 한곳으로 모으기’는 이번 범위입니다. ‘시험 합격 기준을 더 엄격하게 바꾸기’는 결과가 달라지는 정책 수정이므로 별도로 다루어야 합니다.

개발 단계에서 확인할 용어는 다음 정도면 충분합니다.

| 용어 | 이 문서에서의 의미 |
|---|---|
| Backend | 주문·진단·저장을 실제로 처리하는 서버 코드 |
| MCP | 진단 에이전트가 서버의 분석·수정·시험 도구를 호출하는 연결 방식 |
| API 약속 | 요청 필드, 응답 필드, 오류 코드 등 호출자가 기대하는 규칙 |
| 책임 분리 | 조회·판단·실행·저장을 각각 이해하기 쉬운 단위로 나누는 것 |
| 회귀 검증 | 내부 코드를 바꾸어도 기존 입력에 기존 결과가 나오는지 확인하는 것 |

## 2. PM 관점에서 먼저 보실 내용

현재 기능의 수를 늘리는 작업보다, **같은 수정 때문에 여러 파일을 함께 고쳐야 하는 구조와 변경 영향을 파악하기 어려운 구조를 줄이는 작업**을 먼저 권합니다.

| 순서 | 묶음 | 기대 효과 |
|---|---|---|
| 1 | 코드 형식·명칭·주석·설정 설명 정리 | 담당자가 코드를 찾고 이해하는 시간 단축 |
| 2 | MCP 응답·HTTP 연결·데이터 변환의 중복 정리 | 같은 수정의 누락 방지, 장애 원인 추적 용이 |
| 3 | 큰 함수·Controller·진단 단계의 책임 분리 | 변경 범위를 좁히고 리뷰·테스트를 하기 쉬워짐 |
| 4 | 중복된 Skill 해석 코드와 조회 구현 정리 | 규칙의 차이를 관리하고 불필요한 DB 작업 감소 |

이는 권장 착수 순서입니다. 실제 소요 기간은 담당 개발자가 변경 단위와 필요한 검증 범위를 나눈 뒤 산정하는 것이 좋겠습니다.

## 3. 구체적인 리팩토링 항목과 이유

### ① 한 줄에 몰린 코드와 이름을 읽기 쉽게 정리하기

- **현재 상태:** 일부 Java 클래스는 여러 필드와 실행문을 한 줄에 작성하고 있습니다. 반복되는 문자열과 짧은 변수명도 있어 처리 순서와 예외 경계를 한눈에 읽기 어렵습니다.
- **왜 필요한가요?** 작은 조건을 수정할 때도 주변 로직을 다시 해석해야 합니다. 코드 리뷰에서 빠진 조건이나 잘못된 실행 순서를 발견하는 데 시간이 더 걸립니다.
- **정리 방향:** 자동 포맷을 적용하고, 역할을 드러내는 이름을 사용하며, 반복되는 상태·이벤트 이름을 적절한 상수로 정리합니다. 설명이 필요한 트랜잭션 경계에는 이유를 주석으로 남깁니다.
- **완료 기준:** 주문 처리·저장·복구의 순서를 코드에서 따라갈 수 있고, 기존 테스트 결과와 외부 응답은 같습니다.

주요 대상: `DryRunService`, `DiagnosisController`, 주문 `EvidenceController`, `OrderToolService`.

### ② API 입구에서 직접 처리하는 일을 내부 담당 코드로 옮기기

- **현재 상태:** `DiagnosisController`는 요청을 받는 역할뿐 아니라 외부 서버 연결 설정, 토큰 전달, HTTP 호출도 직접 담당합니다. 주문 `EvidenceController`도 snapshot 응답 구성과 파일 인코딩 처리를 함께 수행합니다.
- **왜 필요한가요?** 연결 방식을 바꾸는 작업이 API 처리 코드까지 건드리게 됩니다. 요청을 받는 문제인지, 외부 연결 문제인지, 데이터 변환 문제인지 구분하기도 어렵습니다.
- **정리 방향:** Controller는 요청·응답 연결에 집중하고, 외부 호출은 전용 클라이언트, 응답 변환은 별도 변환 함수로 옮깁니다.
- **완료 기준:** 기존 API 주소·인증·응답·오류는 유지하면서, 외부 연결과 데이터 변환을 각각 독립적으로 확인할 수 있습니다.

예를 들어 진단 서버의 연결 설정을 수정할 때, 제안서 조회나 사용자 요청 처리까지 다시 읽지 않아도 되는 구조를 목표로 합니다.

### ③ 주문 실행의 큰 함수를 단계별로 나누기

- **현재 상태:** `OrderHarness.execute`는 실행 시작, 파일 고정, Skill 선택, 순서 검사, 단계 실행, 종료, 오류 보상을 한 흐름에서 처리합니다. `OrderToolService.execute`도 여러 업무 도구의 처리를 한 메서드에 담고 있습니다.
- **왜 필요한가요?** 배송 처리의 작은 수정도 재고·결제·실패 복구 코드와 함께 검토해야 합니다. 변경 영향이 넓어 보이기 때문에 개발자와 리뷰어가 확인할 양이 커집니다.
- **정리 방향:** 현재 순서를 유지하면서 ‘실행 준비’, ‘단계 실행’, ‘업무 종료’, ‘실패 처리’를 이름 있는 함수로 나눕니다. 도구별 처리도 필요에 따라 작은 단위로 분리합니다.
- **완료 기준:** 각 단위의 역할이 명확하고, DB 저장 시점·도구 실행 순서·재고 보상·실행 기록이 기존과 같습니다.

이 작업은 함수 길이만 줄이는 것이 목적이 아닙니다. 결제 처리 변경이라면 결제 관련 단위부터 확인할 수 있게 만드는 것이 목적입니다. 특히 코드 이동 때문에 DB 트랜잭션 범위가 달라지지 않도록 검증해야 합니다.

### ④ MCP 성공·오류 응답을 만드는 중복 코드 모으기

- **현재 상태:** `ToolResults`와 `WorkspaceToolResults`는 유사한 성공 응답과 오류 JSON을 각각 만듭니다. 다만 처리하는 예외 종류에는 차이가 있습니다.
- **왜 필요한가요?** 응답 필드 하나를 수정하거나 공통 변환 문제를 고칠 때 두 곳을 함께 확인해야 합니다. 한쪽만 수정하면 같은 MCP 도구들 사이에서도 결과 형식이 달라질 수 있습니다.
- **정리 방향:** JSON 응답을 조립하는 부분을 공통화하고, 도구별 예외 처리 차이는 명시적으로 유지합니다.
- **완료 기준:** 공통 응답 구조는 한곳에서 관리하면서 `isError`, 오류 코드, 재시도 가능 여부, 기존 예외 처리 방식은 그대로 유지합니다.

단순히 두 클래스를 합쳐 모든 예외를 똑같이 처리하면 호출자의 동작이 달라질 수 있습니다. 공통화할 부분과 현재 차이를 구분하는 작업이 필요합니다.

### ⑤ 문자열로 꺼내 쓰는 데이터를 내부 타입으로 정리하기

- **현재 상태:** 제안서·실행 기록 등의 데이터를 `Map`이나 Python `dict`에서 필드 이름 문자열로 꺼내는 코드가 많습니다. 이름과 자료형을 여러 함수에서 반복해서 알아야 합니다.
- **왜 필요한가요?** 필드 이름을 잘못 쓰거나 숫자·문자열을 혼동해도 실제 해당 경로가 실행될 때까지 발견하지 못할 수 있습니다. 데이터 구조를 이해하려고 여러 파일을 오가게 됩니다.
- **정리 방향:** 내부 처리에서 반복 사용하는 데이터부터 이름과 자료형이 명시된 객체로 정리하고, 외부 JSON과의 변환을 경계에 모읍니다. 확장 가능한 원문 데이터가 필요한 곳은 보존합니다.
- **완료 기준:** 내부에서는 필드 의미를 쉽게 찾을 수 있고, 외부 API의 필드명·기본값·null 처리·추가 필드 처리 방식은 기존과 같습니다.

여기서 입력 검증을 갑자기 강화하면 기존에 받던 요청이 거부될 수 있습니다. 이번 작업에서는 데이터 표현을 정리하고, 입력 허용 범위를 바꾸는 작업은 분리하는 것이 좋겠습니다.

### ⑥ 외부 HTTP 연결 설정과 오류 해석을 정리하기

- **현재 상태:** Java와 Python의 여러 클라이언트가 주소, 연결 대기 시간, 응답 대기 시간, 오류 해석을 각각 관리합니다. Python에는 주문 서버 주소를 해석하는 설정 경로도 둘 있습니다.
- **왜 필요한가요?** 같은 주문 서버를 호출하더라도 어떤 설정을 따라가는지 파악하기 어렵습니다. 장애 조사 시 요청 경로마다 다른 연결·오류 처리 코드를 확인해야 합니다.
- **정리 방향:** 각 언어 안에서 공통 연결 구성과 설정 접근 방식을 정리하고, 조회용·실행용 정책 차이를 이름으로 드러냅니다. 서비스 주소를 읽는 우선순위도 문서와 코드에서 확인할 수 있게 합니다.
- **완료 기준:** 어떤 호출이 어떤 주소·대기 시간·재시도 정책을 쓰는지 한곳에서 확인할 수 있고, 현재 호출 동작은 유지합니다.

조회와 실행의 재시도 정책은 다를 이유가 있습니다. 예를 들어 주문 실행을 자동 재전송하면 중복 실행될 수 있으므로, 공통화 과정에서 모든 호출에 같은 재시도를 적용해서는 안 됩니다.

### ⑦ Skill 파일을 읽는 코드의 공통 부분과 차이를 정리하기

- **현재 상태:** 주문 실행기, MCP 정적 분석, workspace의 버전 조회가 Skill 파일을 각각 해석합니다. 전체 내용을 검증하는 곳과 필요한 항목만 읽는 곳의 규칙이 다릅니다.
- **왜 필요한가요?** 개발자는 어느 해석 결과를 기준으로 수정해야 하는지 먼저 파악해야 합니다. 파일 형식이 바뀌면 여러 구현을 확인해야 하므로 수정 누락 가능성도 커집니다.
- **정리 방향:** 각 해석기의 용도와 현재 규칙 차이를 정리한 뒤, 실제로 동일한 파싱·데이터 변환 부분부터 공유합니다. 여러 서비스는 같은 정상·불량 예제 파일로 차이를 확인하도록 정리합니다.
- **완료 기준:** 같은 처리는 중복되지 않고, 용도에 따라 다른 처리는 명시되어 있습니다. 기존에 허용·거절하던 입력은 의도 없이 달라지지 않습니다.

현재 서로 다른 검증 규칙을 일괄 통일하는 것은 동작 변경을 포함할 수 있습니다. 우선 리팩토링에서는 공통 부분과 차이를 드러내고 관리하는 데 집중하는 것이 좋겠습니다.

### ⑧ Python 진단 단계에서 조회·판단·실행·저장 역할 나누기

- **현재 상태:** `nodes.py`의 일부 함수는 증거 조회, 파일 비교, 시험 호출, 결과 해석, 상태 구성까지 함께 담당합니다. 특히 `fetch_evidence`와 `verify_candidates`의 역할이 큽니다.
- **왜 필요한가요?** ‘자료를 못 읽은 문제’와 ‘시험 결과가 기대와 다른 문제’를 같은 긴 함수에서 찾아야 합니다. 한 분기를 수정했을 때 다른 진단 경로에 미치는 영향을 확인하기도 어렵습니다.
- **정리 방향:** 자료 조회, 순수한 비교·변환, 시험 요청 구성, 결과 집계 함수를 추출합니다. 진단 node에는 이 단위를 어떤 순서로 부를지 드러나도록 정리합니다.
- **완료 기준:** 기존 그래프 분기·시험 호출 횟수·오류 종료·진행 기록은 같고, 각 처리 단위를 별도로 이해하고 검증할 수 있습니다.

합격 조건을 바꾸거나 모델의 판단 방식을 변경하는 작업은 이 리팩토링에 포함하지 않습니다.

### ⑨ 이전 승인 코드와 현재 실행 경로를 구분하기

- **현재 상태:** 현재 진단 그래프는 제안서를 저장하고 종료하지만, Python에는 이전 승인 대기 함수와 승인 재개용 API가 남아 있습니다. 현재 Java 승인 흐름은 이 경로를 호출하지 않습니다.
- **왜 필요한가요?** 새 담당자가 남아 있는 함수를 보고 ‘승인이 이 경로로 전달된다’고 오해할 수 있습니다. 잘못된 위치를 수정하거나 같은 처리를 다시 구현할 가능성이 있습니다.
- **정리 방향:** 현재 호출 관계와 호환 코드의 역할을 명시하고 관련 코드를 구분합니다. 삭제는 실제 사용 여부와 외부 호출자를 확인한 뒤 별도로 판단합니다.
- **완료 기준:** 현재 승인 처리의 시작과 끝을 문서·코드에서 동일하게 따라갈 수 있습니다. 기존 외부 API를 검토 없이 제거하지 않습니다.

이번 목표는 승인 기능을 확장하는 것이 아니라, 현재 동작을 읽을 때 혼동하지 않게 만드는 것입니다.

### ⑩ 최근 실행 목록에서 불필요한 DB 조회 줄이기

- **현재 상태:** 최근 실행 목록은 각 실행의 상세 기록을 읽은 뒤, 목록에 필요 없는 이벤트를 제거하여 반환합니다. 목록은 최대 20건이지만 내부에서는 상세 조회가 반복됩니다.
- **왜 필요한가요?** 사용자에게 간단한 목록만 보여 줄 때도 상세 기록을 읽는 비용이 발생합니다. 실행 기록이 길어질수록 화면에 필요하지 않은 데이터 처리량이 늘어납니다.
- **정리 방향:** 목록에 필요한 필드만 조회하는 내부 쿼리로 바꿉니다. 상세 기록 API는 기존 역할을 유지합니다.
- **완료 기준:** 반환 필드·건수·정렬·null 처리·오류 응답은 같고, 조회 횟수와 읽는 데이터량이 줄어든 것을 확인할 수 있습니다.

주요 대상: 주문 `ExecutionRepository.recent`, `summary`, `get`.

### ⑪ 현재 설정·주석·호출 예제를 실제 코드에 맞추기

- **현재 상태:** 일부 주석은 이미 해결된 인자 불일치를 여전히 TODO로 설명하고 있습니다. 이전 MCP 도구 개수나 인자 이름을 사용하는 문서·예제도 남아 있습니다. 가짜 응답을 쓰는 개발 설정과 실제 서비스 연결 설정도 구분해서 읽어야 합니다.
- **왜 필요한가요?** 담당자가 문서대로 진행했는데 호출이 실패하거나, 이미 구현된 연결을 다시 작업할 수 있습니다. 인수인계와 시연 준비에서 불필요한 확인 시간이 발생합니다.
- **정리 방향:** 현재 코드에 맞게 주석·예시·설정 설명을 정리하고, 실제 호출 경로와 개발용 경로를 표시합니다. 실행 모드나 기본 동작의 변경은 별도로 검토합니다.
- **완료 기준:** 문서의 도구명·인자명·호출 관계가 구현과 일치하고, 설정을 어떤 프로세스에 전달해야 하는지 명확합니다.

## 4. PM께서 기대하실 수 있는 결과

| 확인할 결과 | 판단 방법 |
|---|---|
| 수정할 위치를 쉽게 찾을 수 있음 | 주문·진단·도구 응답별 담당 코드가 명확함 |
| 한 수정 때문에 여러 곳을 고치는 일이 줄어듦 | 중복된 응답 조립·변환·연결 설정이 공통 단위로 정리됨 |
| 변경 영향이 좁아짐 | 큰 함수에서 분리된 단위별로 리뷰와 검증이 가능함 |
| 인수인계 혼선이 줄어듦 | 현재 경로·호환 코드·개발용 설정의 구분이 문서와 일치함 |
| 사용자는 기존과 같은 기능을 이용함 | 기존 요청·응답·업무 결과·저장 효과의 회귀 검증을 통과함 |

‘코드 줄 수 감소’만을 완료 기준으로 삼기보다는, 변경 책임이 명확해졌는지와 기존 동작이 보존됐는지를 함께 확인하시는 것이 좋겠습니다. 리팩토링만으로 새로운 업무 기능이나 강화된 검증 정책이 완성되는 것은 아닙니다.

## 5. 진행 방식과 검증 기준

한 번에 전체 구조를 바꾸기보다 작은 변경 단위로 진행하는 것을 권합니다.

1. **현재 동작을 기준으로 고정합니다.** 관련 API·오류·업무 결과·저장 순서를 확인하고 기존 테스트를 기준으로 삼습니다. 보존해야 할 동작에 검증이 부족한 경우 해당 경계의 회귀 사례를 보완합니다.
2. **형식과 구조 변경을 나눕니다.** 자동 포맷 작업과 함수·클래스 이동을 분리하면 리뷰어가 실제 구조 변경을 확인하기 쉽습니다.
3. **한 경계씩 공통화합니다.** MCP 응답, HTTP 연결, 내부 데이터 변환 등을 각각 정리합니다. 서로 다른 재시도·예외·검증 정책은 유지합니다.
4. **저장·복구가 관련된 변경은 DB 검증을 포함합니다.** 주문·재고·보상·실행 기록의 트랜잭션 범위가 같아야 합니다.
5. **발견한 버그 수정은 별도로 기록합니다.** 리팩토링 중 문제가 발견되더라도 합격 기준·인증·업무 정책을 함께 바꾸지 않고 영향과 검증을 구분합니다.

이전 코드 검토에서 Java 기본 테스트와 Python 테스트, 두 프런트엔드 빌드는 통과했습니다. 다만 주문 DB 통합 테스트 42개는 해당 실행에서 제외되었습니다. 따라서 위 구조 변경의 완료 여부는 **변경 후 관련 테스트를 다시 실행한 결과**로 판단해야 합니다. 이 문서는 리팩토링 제안이며 구현 완료 보고서는 아닙니다.

## 6. 범위 합의 시 유의사항

앞서 논의한 시험 합격 기준 강화, 실제 실행 근거를 이용한 합격 판정 보강, 인증 확대, 시험 데이터 격리, 새로운 재시도·복구 정책, 승인 후 운영 반영은 서비스 동작이나 제공 범위에 영향을 줍니다. 이 항목들은 이번 리팩토링 일정과 분리하여 기능·정책·결함 수정 과제로 관리하는 것이 좋겠습니다.

이번 작업은 **기존 주문·진단·MCP 기능의 내부 구조를 정리하고, 같은 동작을 더 적은 수정 지점과 명확한 책임으로 유지하는 것**을 목표로 제안드립니다.

개발자가 근거를 확인할 때는 [구조·개선 리뷰](architecture-review.md), [함수 역할 안내](function-reference.md), [Backend API 명세](backend-api.md), [MCP 명세](mcp-spec.md)를 함께 참고할 수 있습니다.
