# 주문 Agent · SkillOps 연계 시나리오

팀 공유용 / 2026-10-20

주문 Agent는 Skill을 실행하고 실제 실패 증거를 남긴다. SkillOps 진단 Agent는 그 증거와 실행 당시 파일을 조사해 원인을 설명하고 수정 후보를 만든다. **현재 주문 앱에는 진단 Agent·Runner·Judge가 연결되지 않았다.** 아래의 진단·수정 후 평가는 연결 이후의 목표이며, 화면의 수정본은 개발자가 준비한 파일이다.

## 시나리오 목록과 현재 재현 범위

| 번호 | 상황 | 구분 | 현재 재현 방법 |
|---|---|---|---|
| 1 | 정상 주문 | 비교 기준 | 화면 정상본 |
| 2 | 재고 부족·결제 거절 | 정상적인 업무 실패 | 화면 주문 예시 |
| 3 | 재고 Skill의 출력 선언 누락 | Skill 계약 결함 | 화면 결함본·수정본 |
| 4 | 배송 예약을 결제 앞으로 이동 | Skill 흐름 결함 | 추가 fixture 필요 |
| 5 | 마지막 알림 단계 누락 | 불완전한 업무 흐름 | 자동 통합 테스트, 화면 fixture 없음 |
| 6 | 존재하지 않는 Skill 선택 | 선택 오류 | 자동 통합 테스트의 응답 주입, 화면 fixture 없음 |
| 7 | 결제 도구에 잘못된 금액 전달 | 도구 인자 오류 | 자동 통합 테스트의 응답 주입, 화면 fixture 없음 |

화면 주소는 http://localhost:5174 이다. **주문 입력 → 후보 고정 → 주문 실행** 순서로 시연한다. 입력 예시를 다시 고르면 후보 선택도 초기화된다. 성공·결제 거절 시나리오는 실제 남은 재고를 먼저 확인한다. 각 비교 실행에는 새 요청 키를 사용한다.

## 1. 정상 주문: 비교 기준 확보

- 입력: `c_1001`, 재고가 있는 캠핑 랜턴 1개, `card`, 국내 배송, 준비된 정상본.
- 실행: `order-flow` → `order-intake` → `inventory-check` → `payment` → `shipping-reserve` → `notify`.
- 관찰: 실제 Skill 파일 로드와 도구 요청·결과가 trace에 남고, 주문은 `SHIPPED`가 된다. 이 상태는 데모에서 배송 예약 완료를 뜻한다.
- 활용: 결함 후보·수정 후보와 비교할 기준 실행으로 보존한다. 정상 실행 자체에 Skill 수정은 필요 없다.

## 2. 재고 부족·결제 거절: 업무 거절과 결함 구분

### 재고 부족

- 입력: 준비된 정상본, 재고가 0인 `CAMP-MUG-STEEL` 1개.
- 관찰: 재고 도구가 정상적인 부족 응답을 반환하고 주문은 `REJECTED`. 결제·배송·성공 알림은 실행하지 않는다.
- 진단 기준: 주문이 완료되지 않았다는 이유만으로 Skill 결함으로 판정하면 안 된다. 재고 결과와 후속 실행 중단이 업무 규칙에 맞는지 확인한다.

### 결제 거절

- 입력: 준비된 정상본, `c_declined`, 재고가 있는 상품 1개, `card`.
- 관찰: 결제 거절 후 주문은 `HOLD`, 재고 예약은 해제된다. 배송·성공 알림은 실행하지 않는다.
- 비교: 같은 고객도 새 주문에서 `prepaid`를 사용하면 성공한다.
- 진단 기준: 결제 거절 자체는 정상 업무 결과다. 거절 이후 배송을 실행하거나 재고 예약을 남기는 경우를 결함으로 조사한다.

## 3. 재고 출력 누락: 현재 화면에서 가능한 핵심 결함 시연

**변경 의도:** 재고 결과에 예약 가능 수량을 표현하려고 출력 선언을 수정했다.

**결함:** `inventory-check`에서 다음 단계가 사용하는 `inventory.reserved` 출력 선언까지 제거했다. `payment`는 여전히 이 값을 필수 입력으로 요구한다.

1. 동일한 주문 입력으로 준비된 결함본을 고정하고 실행한다.
2. Harness가 전체 흐름의 입출력 계약을 검사하다가 차단한다. 재고·결제 등 업무 도구는 아직 실행하지 않는다.
3. 주문은 `FAILED`가 되고 다음 증거가 기록된다.

```json
{
  "category": "CONTRACT_VIOLATION",
  "skill_id": "payment",
  "phase": "static_validation",
  "missing_inputs": ["inventory.reserved"],
  "missing_dependencies": []
}
```

여기서 **실패 Skill은 입력을 받지 못한 `payment`**다. 실제 수정 원인은 앞 단계인 `inventory-check`일 수 있다. 오류에 표시된 Skill과 수정할 파일이 반드시 같지는 않다.

**SkillOps가 조사할 내용:** 기준 snapshot과 결함 snapshot의 차이, `payment.inputs`와 `inventory-check.outputs`, 실제 도구 실행 여부를 함께 확인한다.

**수정 후보:** 새 수량 필드의 의도는 유지하면서 `inventory.reserved` 선언을 복구한다. 이미 저장된 결함 snapshot을 덮어쓰지 않는다.

**수정 후 기준:** 별도 수정 snapshot으로 같은 주문 조건을 실행해 계약 검사가 통과하고 필요한 도구·인자가 맞는지 확인한다. 재고가 있으면 `SHIPPED`, 재고가 없으면 정상적인 `REJECTED`가 되어야 한다. 현재 준비된 수정본 버튼으로 이 비교가 가능하다.

## 4. 배송 예약 순서 변경: 선행 단계·입력 누락

**추가 fixture 제안:** flow를 `order-intake → inventory-check → shipping-reserve → payment → notify`로 변경한다. 현재 화면 버튼에는 없다.

- 관찰 예상: `shipping-reserve`에 필요한 `payment.id`, `payment.status`가 없고 선행 단계 `payment`도 완료되지 않았다. 정적 계약 검사에서 `CONTRACT_VIOLATION`으로 차단되어야 한다.
- 예상 상세: `skill_id=shipping-reserve`, `phase=static_validation`, `missing_inputs=[payment.id, payment.status]`, `missing_dependencies=[payment]`.
- SkillOps 조사: flow 순서 변경과 배송 Skill의 입력·의존성 선언을 함께 비교한다.
- 수정 후보: 실제 배송 예약은 결제 뒤로 복구한다. 변경 의도가 “결제 전에 배송 가능 지역 확인”이었다면, 조회 전용 단계와 실제 예약 단계를 나누는 추가 설계를 제안한다. 현재 조회 전용 도구는 없다.
- 수정 후 기준: 미결제 주문에는 배송 예약이 없어야 하며 정상 주문은 완료되어야 한다. 순서만 되돌리는 것으로 원래 변경 목적을 놓치지 않도록 리뷰한다.

## 5. 알림 단계 누락: 일부 업무 성공을 전체 성공으로 오인

**결함:** flow에서 마지막 `notify` 단계를 제거한다. 자동 통합 테스트에서 검증하며 화면 fixture는 없다.

- 관찰: 앞 단계의 재고 예약·결제 승인·배송 예약은 수행될 수 있지만 마지막에 `INCOMPLETE_FLOW`로 실패한다. 전체 주문을 `SHIPPED`로 확정하지 않는다.
- 보존 정책: 이미 승인된 결제와 배송 예약은 보존하며 자동 환불하지 않는다. 실패했다는 이유로 실제 업무 효과까지 사라졌다고 가정하면 안 된다.
- SkillOps 조사: 기준 flow와 변경 flow, 마지막 실제 도구 결과, 최종 주문 상태를 확인한다.
- 수정 후보: 필요한 알림 단계를 복구한다. 알림을 선택 사항으로 바꾸려는 요구라면 성공 기준 자체를 별도 합의해야 한다.
- 수정 후 기준: 새 테스트 데이터에서 필요한 단계가 모두 완료되어야 한다. 기존 실패 주문을 무작정 재실행해 중복 결제·배송을 만들지 않는다. 현재 수정 후 비교는 새 주문으로 수행한다.

## 6. 존재하지 않는 Skill 선택: 원래 응답 보존

**결함:** 모델이 제공 후보에 없는 `order-fast` 같은 이름을 반환한다. 자동 테스트의 응답 주입으로 재현하며 현재 고정 응답 화면은 임의 이름 입력을 지원하지 않는다.

- 관찰: 원래 이름은 보존하고 `UNKNOWN_SKILL`로 실제 로드를 거부한다. 정상적인 미선택과 구분한다.
- SkillOps 조사: 실제 제공 후보, 모델 원래 응답, 이름 해석 결과, 선택 프롬프트와 메타데이터를 확인한다.
- 수정 후보: 원인에 따라 설명·선택 지침 또는 응답 처리 코드를 수정한다. 없는 이름을 정상 Skill로 몰래 치환하지 않는다.
- 수정 후 기준: 제공된 유효 Skill을 선택하고 실제 파일을 로드해야 한다. 명시적인 미선택은 별도 정상 분기로 평가한다. 틀린 선택을 정답이 나올 때까지 재시도하지 않는다.

## 7. 잘못된 결제 인자: 모델 응답과 서버 계산값 불일치

**결함:** 결제 도구 요청에 서버가 계산한 주문 금액과 다른 값을 넣는다. 자동 테스트의 응답 주입으로 재현하며 화면 fixture는 없다.

- 관찰: `INVALID_TOOL_ARGUMENTS`로 결제를 차단한다. 이미 재고가 예약됐다면 결제 전 오류 정책에 따라 해제하고 주문은 `FAILED`가 된다.
- SkillOps 조사: 고정된 Skill 파일, 모델 응답, 실제 도구 요청, 서버 계산 금액을 비교한다. Skill 설명 문제인지, 모델의 인자 생성 문제인지, 서버 매핑 문제인지 구분한다.
- 수정 후보: 원인이 확인된 부분만 수정한다. 모든 오류를 Skill 문서 수정만으로 해결한다고 가정하지 않는다.
- 수정 후 기준: 서버 기준 금액으로만 결제가 실행되고, 차단된 요청에서는 결제 효과가 없어야 한다. 잘못된 인자 실패 시 예약 해제도 확인한다.

## 담당자 간 전달할 증거

| 정보 | 목적 |
|---|---|
| `execution_id`, `order_id` | 어떤 주문 실행에서 발생했는지 식별 |
| trace 조회 참조 | 제공 후보·원래 응답·실제 로드·도구 효과·오류 확인 |
| `snapshot_id`, snapshot 해시 | 실행 당시 파일을 정확히 다시 조회 |
| 기준 snapshot과 후보 snapshot 참조 | 변경된 파일과 선언을 비교 |
| 오류 category와 상세 | 실패 Skill·누락 입력·발생 단계를 확인 |
| 최종 주문 상태·업무 도구 결과 | 결제·예약 등 이미 발생한 효과를 확인 |
| 진단 run 참조·evaluation 참조 | 해당 기능 연결 후 진단과 평가 기록을 연결 |

현재 앱의 `run_id`는 실행 trace 조회용 별칭이다. 향후 **진단 Agent의 run ID와 같은 값이라고 가정하지 않는다.** 없는 진단·평가 ID를 임의로 생성해 연결된 것처럼 표시하지 않는다.

조회 인터페이스는 `GET /api/executions/{execution_id}/trace`, `GET /api/snapshots/{snapshot_id}`, `GET /api/snapshots/{snapshot_id}/files?path=...`를 사용한다. 전달 payload·실패 이벤트 전송·공용 저장소 연결은 담당자 간 계약 확정이 필요하다. [현재 인터페이스와 연결 TODO](agent-evidence.md)를 참고한다.

## 연계 후 수정 전후 비교 흐름

```text
주문 실행 → Harness가 실제 실패 증거 저장
         → SkillOps가 trace + snapshot + 기준 대비 diff 조사
         → 별도 수정 후보 완성·고정
         → Runner가 동일 Harness로 기준/결함/수정 후보 실행
         → Judge가 시나리오 기대값과 실제 결과 비교
         → 평가 결과를 검토해 승인·반영
```

비교 실행마다 재고·결제 Mock 데이터를 독립적으로 초기화해야 한다. 일반 주문 화면은 재고가 누적 변경되므로 Runner의 격리 환경을 대신하지 않는다. 기대값은 Judge에만 전달하고 주문 Agent의 모델 입력에는 넣지 않는다. 반복 평가와 API 일시 오류 재시도를 분리하고, 미실행·평가 오류·시간 초과를 통과로 처리하지 않는다.

추천 팀 시연은 **정상본 → 결함본의 payment 누락 입력 확인 → snapshot 파일 차이 확인 → 준비된 수정본 비교** 순서다. 이때 마지막 단계가 자동 수정 시연은 아니라는 점을 함께 설명한다.
